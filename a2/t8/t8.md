# Code Refactoring Summary: Separation of Concerns

## Overview
Refactored the task management code to improve separation of concerns, reduce duplication, and improve maintainability while keeping all existing behavior intact.

## Issues Identified

### 1. Duplicate Validation Logic
- Status and priority validation patterns hardcoded in schemas
- Values repeated across multiple files with no single source of truth
- Difficult to maintain and update across the codebase

### 2. Mixed Concerns in Services
- Services directly performed SQLAlchemy queries AND database operations
- Tightly coupled to SQLAlchemy implementation
- Database access logic mixed with business logic

### 3. Repetitive Error Handling
- Each route handler had to check for None and raise HTTPException
- Same error handling code repeated 3 times
- 404 error messages hardcoded in routes

### 4. Unclear Dependencies
- Routes directly referenced database sessions
- No clear data access abstraction layer
- Hard to test services in isolation

## Refactoring Changes

### 1. **New File: `app/constants.py`**
Centralized all configuration constants:
- Valid status/priority values
- Pattern definitions for validation
- Default values for pagination and fields
- Maximum limits for constraints

**Benefits:**
- Single source of truth for all constants
- Easy to update validation rules globally
- Constants can be imported wherever needed

### 2. **New File: `app/repository/task.py`**
Created repository layer for data access:
- `TaskRepository` class encapsulates all database operations
- Separates query building from business logic
- Methods: `list_all()`, `get_by_id()`, `create()`, `update()`, `delete()`

**Benefits:**
- Services no longer directly use SQLAlchemy
- Easy to swap database implementation without changing services
- Clear separation of data access concerns
- Easier to mock for testing

### 3. **New File: `app/exceptions.py`**
Created custom exception for HTTP errors:
- `TaskNotFound` exception with automatic 404 status code
- Eliminates repetitive error handling in routes
- Consistent error responses

**Benefits:**
- DRY principle: raise once, use everywhere
- Consistent error format across all routes
- Easy to add more custom exceptions in future

### 4. **Updated: `app/schemas/task.py`**
- Imports constants from `app/constants.py`
- Uses `STATUS_PATTERN` and `PRIORITY_PATTERN` instead of hardcoded strings
- Uses `DEFAULT_STATUS` and `DEFAULT_PRIORITY` for defaults

**Benefits:**
- Schema validation centralized
- Validation rules defined in one place
- Easier to maintain and update

### 5. **Refactored: `app/services/task.py`**
- Services now use `TaskRepository` instead of direct SQLAlchemy
- Added `get_repository()` helper function
- Simplified business logic by delegating data access

**Before:**
```python
def list_tasks(db, status, priority, limit, offset):
    query = db.query(Task)  # Direct SQLAlchemy
    if status:
        query = query.filter(Task.status == status)
    # ... more query building
    return query.order_by(Task.id).limit(limit).offset(offset).all()
```

**After:**
```python
def list_tasks(db, status, priority, limit, offset):
    repo = get_repository(db)  # Use repository
    return repo.list_all(status=status, priority=priority, limit=limit, offset=offset)
```

**Benefits:**
- Cleaner, more readable code
- No SQLAlchemy imports in services
- Easy to test with mock repository
- Business logic separated from data access

### 6. **Simplified: `app/routes/tasks.py`**
- Uses `TaskNotFound` exception instead of manual HTTPException
- References constants for pagination limits
- Added docstrings for clarity
- Reduced repetitive error handling code

**Before:**
```python
def get_task(task_id: int, db: Session = Depends(get_db)):
    task = task_service.get_task(db, task_id)
    if task is None:
        raise HTTPException(status_code=status.HTTP_404_NOT_FOUND, detail="Task not found")
    return task
```

**After:**
```python
def get_task(task_id: int, db: Session = Depends(get_db)):
    """Get a single task by ID."""
    task = task_service.get_task(db, task_id)
    if task is None:
        raise TaskNotFound(task_id)
    return task
```

**Benefits:**
- Cleaner, less boilerplate code
- Consistent error handling
- Uses constants for configuration
- Clear documentation with docstrings

## Architecture Layers

### Clear Separation of Concerns:

```
HTTP Layer (Routes)
    ↓
Business Logic (Services)
    ↓
Data Access (Repository)
    ↓
Database Models (SQLAlchemy)
    ↓
Database
```

**Each layer has distinct responsibility:**
1. **Routes** - Handle HTTP requests/responses, error handling
2. **Services** - Business logic, coordination
3. **Repository** - Database queries and operations
4. **Models** - Database schema definition
5. **Constants** - Configuration and validation rules

## Principles Applied

1. **DRY (Don't Repeat Yourself)** - Constants defined once, used everywhere
2. **Single Responsibility** - Each module has one job
3. **Dependency Inversion** - Services depend on repository abstraction, not SQLAlchemy
4. **Separation of Concerns** - HTTP, business logic, and data access in different layers
5. **Minimal Abstraction** - No unnecessary complexity, just clear patterns
