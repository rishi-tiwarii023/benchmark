# Changes Summary — Task Title Update Persistence

## Problem

PATCH `/tasks/{id}` with a new `title` could return **200** and a body showing the updated title, but a later **GET** (or list) still showed the old title. Title changes were not reliably persisted.

## Root cause

`update_task` in `app/services/task.py` did not apply `title` when merging partial updates. Status (and other fields) were updated, but **`title` was never written** to the loaded `Task` row before `commit()`, so the database kept the previous value. The in-memory object or response could still look updated depending on how the handler returned data.

## Fix

### `app/services/task.py`
- Build patch fields with `TaskUpdate.model_dump(exclude_unset=True)`.
- Apply **every** included key—including `title`—with `setattr(task, key, value)`.
- Keep `db.commit()` and `db.refresh(task)` so the row matches what clients read back.

No route, schema, or model changes required beyond this service fix.

## Regression test

### `tests/test_tasks_api.py` (or dedicated test module)
- Create a task with a known title.
- `PATCH` with `{"title": "<new>"}` only (or with other fields).
- Assert **GET** on the same `task_id` returns the **new** title (not only the PATCH response body).

This catches “response looks fine, storage does not” failures. Existing `test_update_task` already asserted the PATCH JSON; the regression test emphasizes **read-after-write** via GET.

## Behavior (after fix)

| Step | Expected |
|------|----------|
| `POST /tasks` with `title: "Old"` | 201, title `Old` |
| `PATCH /tasks/{id}` with `title: "New"` | 200, title `New` |
| `GET /tasks/{id}` | 200, title **`New`** (persisted) |

## Verification

```bash
pytest tests/ -k update
```

Run the full suite when convenient: `pytest tests/`.

## Scope

- **Touched:** `app/services/task.py`, tests for title update persistence.
- **Unchanged:** validation rules (t5), list filters (t4), health endpoint, unrelated CRUD paths.

## Investigation notes (thought summary)

1. **API vs storage:** Compare PATCH response with a follow-up GET using the same DB (tests use a shared session override; manual checks should still use GET).
2. **Update merge:** Confirm `title` appears in `model_dump(exclude_unset=True)` for `TaskUpdate` and is applied in the service loop—not only `status` / `priority` / `description`.
3. **Session lifecycle:** `commit()` + `refresh(task)` after all fields are set; no second assignment that resets `title` before flush.
4. **Out of scope for this bug:** Empty DB vs migrated `tasks.db` (e.g. missing `priority` column) is a separate local schema issue, not title persistence logic.
